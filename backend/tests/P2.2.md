# P2.2 — Persistencia y credenciales

Implementación limitada a modelos, migración, primitivas de credenciales y
validación. No añade endpoints, cookies HTTP, login, logout, registro ni
autorización. `POST /api/appointments` mantiene el comportamiento P1.

## Persistencia

- `0004_identity_persistence` sucede a `0003_barbers_and_schedules`; 0001–0003
  no se modifican. Se conserva la exclusión P0 y `barber_id NOT NULL`.
- `users.role` acepta exactamente `owner`, `admin`, `barber`, `client` sin
  default Python. La migración inspecciona el default de servidor y solo lo
  elimina si existe. No realiza backfill ni crea cuentas.
- `barbers.user_id`: nullable, FK `users.id`, `UNIQUE`, `ON DELETE RESTRICT`.
- `appointments.client_user_id`: nullable, FK `users.id`, `ON DELETE RESTRICT`.
  Los contactos históricos y estados de reserva se conservan.
- `auth_sessions`: `id`, `user_id`, `session_token_hash` único,
  `csrf_token_hash`, `created_at`, `expires_at`, `revoked_at` nullable.
  Timestamps con zona. Índice `user_id` para búsqueda de sesiones por cuenta.
  No hay tokens raw, refresh tokens, JWT ni limpieza automática.
- `core.credentials` usa Argon2id real con `argon2-cffi>=25.1,<26`, UTF-8,
  64 MiB, tres iteraciones, paralelismo cuatro, salt aleatorio de 16 bytes
  y hash de 32 bytes. No recorta ni normaliza contraseñas y no añade política
  empresarial. Los tokens aleatorios usan 32 bytes de entropía y SHA-256.

El downgrade elimina únicamente estructuras P2.2 y restaura roles admin/barber.
Si existen cuentas owner/client, se detiene antes de cualquier DDL: no borra
cuentas ni convierte roles. Si se autoriza un downgrade compatible, se perderán
las sesiones y los enlaces de identidad introducidos por 0004. Las pruebas de
downgrade trabajan en esquemas aislados y siempre revierten su transacción;
no degradan tablas públicas ni la base principal.

## Validación y separación de entornos

Las pruebas locales validan modelos, credenciales reales y guards con mocks.
La migración real, FKs, UNIQUE y concurrencia requieren PostgreSQL y no quedan
demostradas por esos mocks. Los fixtures PostgreSQL usan exclusivamente
`logia_barber_p0_test`, verifican URL y `current_database()` y exigen preflight.

El runner exige exactamente 0004 y el esquema P0/P2.2 completo. La modalidad
`--reuse-existing` continúa sin crear, migrar, borrar, sembrar ni conectar con
la base principal. La migración explícita de pruebas es un comando separado:

```fish
cd /home/kevin7/Documentos/LogiaBarber/backend
.venv/bin/python -B -m tests.migrate_p22_test_database
and .venv/bin/python -B -m tests.run_p0_validation --reuse-existing
```

Requiere `P0_TEST_DATABASE_URL` privada para el destino exacto. No pasar la URL
como argumento, no imprimirla y nunca exportar `P0_TEST_PREPARED` manualmente.
El helper solo acepta origen 0003 o head exacto 0004; nunca crea la base ni
modifica privilegios. Los resultados del runner siguen en
`tests/p0_validation_results.json`. El runner exige resultados estructurados
JUnit XML, rechaza suites preparadas con skips o sin casos y elimina
`PYTEST_ADDOPTS` heredado para impedir filtros o formatos que oculten omisiones.
Los XML temporales se eliminan al terminar; el JSON conserva sus cantidades.

## Comandos Fish fuera del sandbox, sin mostrar credenciales

Cuando el sandbox impida instalar dependencias o conectar, este bloque completa
la validación. Primero instala y ejecuta la suite local. Después migra solo la
base de pruebas y ejecuta el runner. Usa la URL privada explícita si existe;
en caso contrario reutiliza las credenciales configuradas en memoria cambiando
únicamente el nombre al destino de pruebas exacto. Nunca conecta a la base
principal. No imprime secretos ni modifica `.env` o la sesión del shell.

```fish
cd /home/kevin7/Documentos/LogiaBarber/backend
.venv/bin/python -B -m pip install -r requirements.txt
and env -u P0_TEST_DATABASE_URL -u P0_TEST_PREPARED .venv/bin/python -B -m pytest -q -p no:cacheprovider tests
and .venv/bin/python -B -c '
import os, sys
from sqlalchemy.engine import make_url
from app.core.config import settings
from tests.p0_database import TARGET, require_target_url
from tests.migrate_p22_test_database import main as migrate
from tests.run_p0_validation import main as validate
raw = os.environ.get("P0_TEST_DATABASE_URL")
if raw is None:
    raw = make_url(settings.database_url).set(database=TARGET).render_as_string(hide_password=False)
try:
    require_target_url(raw)
except Exception:
    raise SystemExit("STOP: destino de pruebas invalido; detalles ocultos")
os.environ["P0_TEST_DATABASE_URL"] = raw
os.environ.pop("P0_TEST_PREPARED", None)
if migrate() != 0:
    raise SystemExit(1)
sys.argv = ["run_p0_validation", "--reuse-existing"]
raise SystemExit(validate())
'
```

No usar aquí el modo de creación inicial ni `alembic upgrade head` sin guards.
P2.2 requiere evidencia nueva: preflight PASS, P0 PostgreSQL, P2.2 PostgreSQL,
suite completa sin omisiones y concurrencias 201+409/201+201. Los resultados
previos 38/38 y 237/237 son históricos; no aprueban esta implementación.

## Evidencia local de esta implementación

- Guardas/runner P0/P2.2 y tests unitarios P0: 111 passed, salida 0.
- Suite local completa con variables PostgreSQL retiradas del subprocess:
  `env -u P0_TEST_DATABASE_URL -u P0_TEST_PREPARED .venv/bin/python -B -m pytest -q -p no:cacheprovider --tb=no tests`.
  Resultado final tras corregir el hallazgo de auditoría:
  **224 passed, 113 skipped, 24 errors**, salida 1.
- Las 113 omisiones requieren PostgreSQL: 38 P0, 35 P1.6 y 40 P2.2.
- Los 24 errores son de preparación por `ModuleNotFoundError: argon2`;
  no se ejecutó hashing real. Instalar `argon2-cffi>=25.1,<26` falló por
  resolución DNS del sandbox y no se encontró distribución local reutilizable.
- Una sonda protegida de solo lectura a la base exacta de pruebas quedó
  bloqueada con `OperationalError`. No se ejecutaron migraciones ni suites
  PostgreSQL y no se conectó a la base principal.
- La sintaxis de los comandos Fish se comprobó con `fish --no-execute`.
- SHA-256 de referencia confirma 0001–0003, API existente y frontend intactos.
- AUDITOR detectó que el resumen textual podía ocultar skips con opciones de
  salida. Se sustituyó por inspección obligatoria de resultados JUnit XML;
  pruebas añadidas cubren salida silenciosa, XML inválido/vacío, errores y
  opciones heredadas. La validación real continúa pendiente.

Esta evidencia es parcial: faltan credenciales reales, migración/preflight y
regresión PostgreSQL antes de considerar P2.2 aprobable.
